Decker Resurrects HyperCard's Spirit for the Modern WebshareCopied!

*A nostalgic stack-based platform proves there's still hunger for interactive computing done differently*
▲ 319 pts  ·  74 comments

Two decades after HyperCard's quiet death, a new platform called Decker is attempting something almost heretical in 2026: proving that the canonical way we build interactive software isn't the only way—or even the best way. Built as a spiritual successor to Apple's legendary hypertext environment and drawing DNA from classic macOS interfaces, Decker lets creators compose multimedia "decks" with a visual programming model that prioritizes immediate feedback and human-scale complexity.

The project arrives at a curious moment. Web development has calcified into a typescript-webpack-react triathlon that demands increasingly baroque tooling just to ship a button. Meanwhile, nostalgia for pre-web computing—when a person could reasonably understand an entire system's architecture—has metastasized from retro communities into something resembling genuine hunger. Decker taps that hunger by offering genuine constraints: its stack-oriented scripting language and card-based architecture feel quaint until you realize they force clarity of thought that contemporary frameworks actively obscure.

What's genuinely provocative here isn't the aesthetics but the implication. If HyperCard could be genuinely productive in 1987, why does modern software require such orders of magnitude more complexity to achieve less? Decker won't displace Electron or the JavaScript industrial complex, but it may prove something deeper: that for certain categories of creation—interactive documents, data visualization, educational software, tools—we've been building with the wrong ontology entirely.

Vercel's Scriptc Strips JavaScript From the Runtime EquationshareCopied!

*A TypeScript-to-native compiler promises to eliminate the engine entirely, radically shrinking binaries*
▲ 203 pts  ·  103 comments

Vercel Labs has shipped Scriptc, a compiler that performs a heretofore elusive trick: consuming TypeScript source and emitting native binaries without embedding a JavaScript engine—no V8, no JavaScriptCore, no runtime overhead at all. The technical audacity here is worth parsing. Most TypeScript-to-native projects have compromised by bundling a lean interpreter or JIT to handle dynamic features; Scriptc instead enforces static typing discipline strictly enough that it can eliminate the runtime layer wholesale.

The implications ripple outward quickly. Binary sizes shrink dramatically—no longer are you shipping megabytes of interpreter overhead for a CLI tool or edge function. Execution becomes predictable; there's no garbage collection pause, no JIT warmup phase. Performance characteristics flatten into what compiled code actually is: fast, immediate, knowable. For Vercel's use case—serverless functions, edge computing, developer tooling—this removes an entire category of complexity from the deployment equation.

But there are real tradeoffs embedded in this architecture. Scriptc works best when your code's types remain fully knowable at compile time, which excludes swaths of legitimate JavaScript patterns. Dynamic dispatch, runtime reflection, metaprogramming—all the techniques that make JavaScript feel alive to many developers—become forbidden. It's a tool for a specific problem class, not a universal replacement. Still, for infrastructure code and tooling, it might be exactly the right constraint.

Data-Oriented Design Resurfaces as Game Industry's Secret WeaponshareCopied!

*A PDF guide to organizing software around data shapes—not objects—gains renewed attention in optimization discourse*
▲ 184 pts  ·  50 comments

An introductory paper on data-oriented design is circulating again through technical communities, and its timing reveals something about where performance anxiety lives in 2026. Rather than organizing code around semantic object models (the entity-component-system paradigm that has dominated game development for a decade), data-oriented design argues for inverting the hierarchy: structure your software around the actual memory layouts and cache behavior of your data, then build logic around those constraints.

The philosophical shift is subtle but consequential. Where OOP thinks "what is this thing?", data-oriented design asks "how does this thing live in memory, and what does the CPU actually see?" It sounds like premature optimization theater until you realize that cache misses—not algorithmic complexity—now dominate real-world performance bottlenecks on modern hardware. A dense, sequential array of `float[4]` processed in tight loops will outperform more semantically elegant code by orders of magnitude, full stop.

The renewed interest suggests the pendulum is swinging back from years of "move fast and let the runtime optimize for you." As systems scale—whether in game engines, data processing, or AI inference—that philosophy has hit a wall. Data-oriented design offers not a complete solution but a vocabulary for thinking concretely about the actual substrate your code runs on. For practitioners working in performance-critical domains, it's less trend than rediscovery.

Formal Verification Cracks Compression: We Now Know Zstandard WorksshareCopied!

*A rigorous mathematical proof of Zstandard's correctness marks a watershed moment for verifying real-world infrastructure*
▲ 178 pts  ·  69 comments

A blog post titled "We have proof automation now" from a verified systems researcher documents something that sounds dry until you understand what it actually means: Zstandard, the compression algorithm shipping in production systems worldwide, has now been formally verified to be correct using Lean, a mathematical proof assistant. Not tested. Not statistically validated. Proven, in the mathematical sense—every possible execution path guaranteed to produce correct output.

This is frontier work. Formal verification has historically remained confined to critical security infrastructure and aerospace systems because the human effort required to construct a proof massively exceeds the complexity of simply implementing and testing code. That calculus is shifting. Modern proof assistants and automated tactics are making it feasible to verify substantial, genuinely useful software. Zstandard is not a toy problem—it's a real compression library with genuine algorithmic sophistication, used in production by organizations that couldn't remotely afford a bug. Getting there required treating the algorithm as mathematics and the code as a machine-checkable theorem.

The significance extends beyond Zstandard itself. If verification automation is advancing to the point where we can prove the correctness of compression algorithms, what's next? Database engines? Cryptographic libraries? The window for formally verified infrastructure—once theoretical luxury—is cracking open into practical reality. The question now is whether the industry will actually adopt these techniques before the next zero-day surfaces.
